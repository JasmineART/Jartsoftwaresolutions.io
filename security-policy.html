JART Software Solutions is committed to maintaining the highest standards of information security across all aspects of our operations — from internal systems to client deliverables. This policy describes our security posture, controls, and practices. It is reviewed and updated at least annually.

1. Our Security Commitment

Security is not a feature at JART Software Solutions — it is a foundational principle. Every solution we architect, every system we build, and every service we deliver is designed with security as a first-order concern. We apply the principle of security by design and by default, ensuring that the most privacy-protective and security-preserving settings are active from day one.

Our security program is aligned with industry-recognized frameworks and standards to protect:

  • Client data, systems, and intellectual property
  • The confidentiality, integrity, and availability of all information assets
  • The privacy rights of all individuals whose data we process
  • The operational continuity of our clients' businesses

2. Security Framework

Our information security management system is aligned with the NIST Cybersecurity Framework (CSF) 2.0 and references ISO/IEC 27001:2022 as a guiding standard. We organize security controls across six NIST CSF core functions:

NIST CSF Function Description Key Activities
Govern Establish and monitor the organization's cybersecurity risk strategy and policies Risk governance, policy management, roles & responsibilities
Identify Develop an understanding of assets, risks, and vulnerabilities Asset inventory, risk assessments, threat modeling
Protect Implement safeguards to ensure delivery of critical services Encryption, access control, secure development, awareness training
Detect Implement activities to identify cybersecurity events Monitoring, anomaly detection, log analysis, alerting
Respond Take action regarding a detected cybersecurity incident Incident response plan, communication, containment, eradication
Recover Maintain resilience and restore capabilities after an incident Recovery planning, backups, post-incident review

3. Data Protection and Encryption

3.1 Data in Transit

All data transmitted between clients, our systems, and third-party services is encrypted using TLS 1.3 (minimum TLS 1.2 where legacy compatibility requires it). We enforce HTTPS with HTTP Strict Transport Security (HSTS) on all web properties. Weak cipher suites and deprecated protocols (TLS 1.0/1.1, SSLv3) are disabled.

3.2 Data at Rest

Sensitive data stored on our systems and in our delivered solutions is encrypted using AES-256 encryption. Database encryption (transparent data encryption) is applied to all production databases containing personal or confidential data. Backup data is encrypted with equivalent strength.

3.3 Key Management

Encryption keys are managed using hardware security modules (HSMs) or equivalent cloud key management services. Keys are rotated on a defined schedule, and access to key material is strictly controlled and audited. Key rotation events are logged and reviewed.

3.4 End-to-End Encryption

For client engagements handling highly sensitive data (healthcare, financial, or similarly regulated data), we implement end-to-end encryption architectures ensuring that data is protected even from the infrastructure layer.

4. Access Control

Our access control framework is built on three core principles: least privilege, need-to-know, and zero-trust.

4.1 Authentication

  • Multi-Factor Authentication (MFA) is mandatory for all internal systems, developer tools, cloud consoles, and client-facing portals
  • Passwords must meet complexity requirements (minimum 16 characters, not reused from previous 12 passwords) and are stored only as salted cryptographic hashes (bcrypt/Argon2)
  • Single Sign-On (SSO) with SAML 2.0 or OIDC is used where technically feasible to reduce credential sprawl
  • Authentication attempts are rate-limited and anomalous login events trigger automated alerts

4.2 Authorization (Role-Based Access Control)

  • Access to all systems is governed by Role-Based Access Control (RBAC). Users are granted only the minimum permissions required to perform their job function
  • Privileged access (administrative/root) requires additional approval, is time-limited, and every action is logged
  • Access rights are reviewed quarterly and upon any change in personnel role
  • Terminated employee or contractor access is revoked within 24 hours of departure

4.3 Zero-Trust Architecture

We apply zero-trust principles: no user or system is implicitly trusted based on network location. Every request is authenticated, authorized, and encrypted regardless of whether it originates from inside or outside our network perimeter. Micro-segmentation is applied to limit lateral movement in the event of a breach.

5. Application Security

We build security into every phase of our Software Development Lifecycle (SDLC) following the OWASP (Open Worldwide Application Security Project) standards.

5.1 Secure Development Practices

  • All developers are trained in secure coding practices, with mandatory annual refreshers
  • OWASP Top 10 and OWASP Application Security Verification Standard (ASVS) are referenced as baselines for all web applications
  • Threat modeling (using STRIDE) is performed for all new systems and significant architectural changes
  • Code review is mandatory for all changes before merging to main branches; security-critical changes require review by a senior security-aware engineer

5.2 Static and Dynamic Analysis

  • Static Application Security Testing (SAST) is integrated into CI/CD pipelines and runs on every code commit
  • Dynamic Application Security Testing (DAST) is performed on staging environments prior to major releases
  • Software Composition Analysis (SCA) continuously monitors all open-source dependencies for known vulnerabilities (CVEs) using industry tooling
  • Critical and high-severity findings in automated scans block deployment until resolved

5.3 Security Testing

All production systems undergo at minimum an annual third-party penetration test. Applications handling sensitive data (healthcare, financial, PII) receive penetration testing prior to production deployment. Findings are remediated within defined SLAs based on severity:

SeverityCVSS ScoreRemediation SLA
Critical9.0–10.024 hours (emergency patch)
High7.0–8.97 days
Medium4.0–6.930 days
Low0.1–3.990 days

6. Infrastructure Security

6.1 Cloud Security

Cloud infrastructure is configured following Center for Internet Security (CIS) Benchmarks for the relevant platform. Infrastructure-as-Code (IaC) templates are security-scanned before deployment. Cloud environments use separate accounts/projects for development, staging, and production environments (environment isolation).

6.2 Network Security

  • Web Application Firewall (WAF) is deployed for all internet-facing applications to protect against OWASP Top 10 attacks
  • DDoS protection is implemented at the network edge
  • Network traffic is monitored using intrusion detection systems (IDS/IPS)
  • All unnecessary ports and services are disabled; network rules follow a default-deny posture

6.3 Endpoint Security

  • All company-managed endpoints use full-disk encryption (FileVault / BitLocker)
  • Endpoint Detection and Response (EDR) software is deployed on all devices with access to client data
  • Automated patch management ensures operating system and application patches are applied within defined SLAs
  • BYOD (bring your own device) access to sensitive systems is restricted or prohibited

7. Vulnerability Management

Our vulnerability management program follows a continuous cycle of discovery, prioritization, remediation, and verification:

  • Asset inventory: All IT assets are catalogued and classified by risk level
  • Continuous scanning: Automated vulnerability scans run weekly against all in-scope systems
  • CVE monitoring: We subscribe to NVD (National Vulnerability Database), CISA KEV (Known Exploited Vulnerabilities), and vendor security advisories
  • Patch management: Critical security patches are evaluated within 24 hours of release; deployment timelines follow the severity-based SLAs above
  • Compensating controls: Where immediate patching is not feasible, risk-accepted compensating controls are documented and reviewed by management

8. Incident Response

Our incident response plan follows NIST SP 800-61 Rev. 2 (Computer Security Incident Handling Guide), covering Preparation, Detection & Analysis, Containment, Eradication, Recovery, and Post-Incident Activity.

8.1 Response Phases

  • Preparation: Documented IR plan, defined roles, tested runbooks, communication templates
  • Detection: 24/7 automated monitoring and alerting; all security events are logged to a centralized SIEM
  • Containment: Isolate affected systems within 1 hour of confirmed incident declaration
  • Eradication: Remove threat actor access and root cause; verify clean state before recovery
  • Recovery: Restore systems from verified clean backups; monitor for reinfection
  • Post-Incident: Root cause analysis, lessons learned, policy and control updates within 30 days

8.2 Breach Notification

In the event of a confirmed personal data breach:

  • Affected clients are notified within 24 hours of confirmation with preliminary details
  • GDPR supervisory authority notification is made within 72 hours where required (GDPR Art. 33)
  • Affected individuals are notified without undue delay where the breach poses a high risk to their rights and freedoms (GDPR Art. 34)
  • HIPAA-covered incidents follow the HIPAA Breach Notification Rule (45 CFR §§ 164.400-414)

9. Third-Party and Vendor Security

We apply rigorous security requirements to all third-party vendors and sub-processors that access our systems or process data on our behalf:

  • All vendors handling personal data sign a Data Processing Agreement (DPA) prior to being granted access
  • Critical vendors undergo security questionnaire review aligned with the Shared Assessments SIG (Standardized Information Gathering) questionnaire
  • Vendors are reviewed annually, and high-risk vendors may be subject to on-site or remote audits
  • Vendor access to our systems is granted on a least-privilege basis and monitored
  • We maintain a list of authorized sub-processors and notify clients of material changes with adequate notice

10. Personnel Security

  • Background screening: All personnel with access to client data undergo background verification appropriate to the sensitivity of their role
  • Security awareness training: All personnel complete security awareness training upon onboarding and annually thereafter, covering phishing, social engineering, incident reporting, and acceptable use
  • Acceptable use policy: All personnel sign and adhere to our Acceptable Use Policy governing the use of company and client systems
  • Confidentiality agreements: All personnel and contractors sign confidentiality agreements before accessing any client or proprietary information
  • Security champions: Designated security champions in each project team are responsible for promoting secure development practices

13. Responsible Vulnerability Disclosure

JART Software Solutions encourages the responsible disclosure of security vulnerabilities affecting our systems or our clients' systems. We are committed to working with security researchers in good faith.

13.1 Scope

In-scope for disclosure reports: this website (jartsoftwaresolutions.com) and production systems directly operated by JART Software Solutions.

Out-of-scope: third-party services (GitHub Pages, etc.), denial-of-service attacks, social engineering of JART personnel, and physical security attacks.

13.2 Disclosure Process

  1. Submit your report via email to security@jartsoftwaresolutions.com
  2. Include a clear description of the vulnerability, steps to reproduce, potential impact, and any proof-of-concept
  3. We will acknowledge receipt within 2 business days
  4. We will confirm the vulnerability and provide an initial severity assessment within 10 business days
  5. We will remediate confirmed vulnerabilities within the SLA timelines defined in Section 5.3
  6. We ask that you do not disclose the vulnerability publicly until we have issued a fix, or until 90 days have elapsed since submission (whichever comes first)

13.3 Safe Harbor

We will not pursue legal action against researchers who discover and report vulnerabilities in good faith, provided they do not access or modify data beyond what is necessary to demonstrate the vulnerability, and do not conduct attacks that could harm the availability or integrity of our systems.
